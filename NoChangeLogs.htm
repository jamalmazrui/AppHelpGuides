No change logs, and the script fetches the manual

One new rule, applied backwards as well as forwards

2026-08-03

No change logs

Your rule, taken as absolute: an app’s change-log history never goes in a help guide. A release note says what changed in a version, not how to do anything, and it is stale the moment the next version ships.

It is now enforced in three places — at harvest, at build, and retrospectively on everything already shipped.

Two lists, because one is not enough

  • Certain terms mean a change log wherever they appear: release notes, changelog, what’s new, new in version, update history, version notes. Refused in an article title as readily as in a category.
  • Ambiguous terms mean a change log only when they name a whole category: version history, recent changes, latest updates, product updates, announcements.

That second list exists because of Dropbox. “Dropbox version history overview” is about a feature of Dropbox — keeping earlier copies of a file — and is exactly the sort of article a reader wants. A category called “Version history” is a change log. Same words, opposite verdicts, and only the level tells them apart.

And every match is on whole words. “What is News and Flash Briefing for Alexa?” contains the letters of “what is new” and is not a change log. My first attempt flagged it. That substring fault has cost this project eight previous corrections; this makes nine, and it was caught before anything was deleted because I checked the report before running the removal.

What it found in the collection

Six whole categories and 171 articles across 28 guides.

  • AndroidStudio — 70 articles and a whole category, “Release notes and known issues”. Comfortably the largest.
  • Audacity 18, Zoom 17, WordPress 13, SmartNews 12, ChatGPT 8. Zoom’s were release notes for Zoom Hub, Zoom Rooms and Revenue Accelerator; WordPress’s were theme changelogs — Twenty Eleven, Twenty Fifteen and the rest.
  • Then a long tail of one or two apiece: Teams, macOS, Squarespace, Dragon, Slack, OneDrive, YouTube, iOS, Goodreads, Indeed and others.

All removed, contents entries with them, and every guide re-ordered and re-audited afterwards. All 127 still pass every structural gate — no ordering broken, no heading skips, no contents entry pointing at anything gone.

dropChangeLog.py runs in report mode first — python dropChangeLog.py <folder> --report — which is how the two false positives were caught. Use that before the removal on anything new.

The script fetches the manual

A publisher’s documentation is not always a page. PiccyBot’s whole manual is a PDF; SOUND FORGE’s is a 520-page one. A harvester that only understands pages walks straight past the thing it came for.

getBrowserHelp.py version 10 collects any link to a document — .pdf, .docx, .doc, .epub, .rtf, .txt, .md — and fetches it alongside the pages, into the same harvest folder, recorded in manifest.txt as a file rather than a page. The log says so loudly:

FETCHED A DOCUMENT: piccybot-manual.pdf (1,284,332 bytes) from ...

and the estate’s summary adds: “A document was fetched. It is very likely the real guide.”

Two details worth knowing:

  • The file is fetched over plain HTTP, not through the browser. A browser asked to open a PDF may render it, save it somewhere of its own choosing, or do nothing at all — and none of those hands the bytes back. The browser finds the link; ordinary HTTP fetches it.
  • Sixty megabytes is the ceiling, and anything larger is named in the log rather than downloaded, so a run cannot be derailed by an installer someone linked from a help page.

Three predicates cover it, including one proving an ordinary page link is not mistaken for a document. 36 of 36 pass.

So run python getBrowserHelp.py piccybot. If the manual is linked anywhere on piccybot.com once rendered, that run will bring it back and we will have the guide. If it is only offered from inside the app, the run will say so by finding nothing — and then I would still like the file from you.

Summary

  • Change-log history is now refused at harvest, at build, and retrospectively: six whole categories and 171 articles removed from 28 shipped guides.
  • Two term lists, because “version history” is a Dropbox feature and a change-log category depending only on which level it sits at.
  • Whole-word matching throughout — “What is News” is not “what is new”, and the report mode caught it before anything was deleted.
  • All 127 guides re-ordered and re-audited; every structural gate still passes.
  • getBrowserHelp.py v10 fetches documents as well as pages, over plain HTTP, capped at 60 MB, and says loudly when it has found one.
  • Run python getBrowserHelp.py piccybot — it may bring back the manual by itself.
