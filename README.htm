App Help Guides

Every guide in this repository is the official, public help documentation published by the makers of the product itself, gathered from their own help centres and reassembled into one Markdown document per product.

Nothing here is a summary, a rewrite, or a third-party explanation. The words are the publisher’s own. What changes is the shape: instead of hundreds of separate web pages wrapped in navigation bars, cookie notices, chat widgets and scripts, each product’s help arrives as a single document that a screen reader can read from top to bottom or jump around by heading.

Why this exists

Modern help centres are built for sighted mouse users. An answer that is three sentences long sits inside a page of several hundred kilobytes, behind an accordion that must be expanded, below a search box that steals focus, beside a chat widget that announces itself. Finding one fact can mean a dozen page loads, each with its own banner to dismiss and its own landmark structure to relearn.

A single document removes all of that. One file, one heading structure, one search. No page loads, no scripts, no consent dialogs. It works offline, on a braille display, in a text editor, or read aloud end to end.

The guides are also comprehensive rather than selective. Where a publisher has a hundred articles about its product, the guide has a hundred articles. Nothing is left out for brevity; anything left out for scope is named.

What is in each guide

Each guide is a Pandoc-flavoured Markdown file with the same shape:

  • A title block giving the product, a subtitle, and the date the material was gathered.
  • A preamble stating where the text came from, on what date, which surfaces the product runs on, what was included, and what was deliberately left out.
  • A table of contents listing every section and every article, each as a link.
  • Sections, then articles, nested three deep: the guide title, a section, an article. Each article’s own subheadings sit beneath it.

Cross references between articles become links inside the document, so following a “see also” never leaves the file.

How the guides are made

Each product follows the same cycle:

  1. The publisher’s own help centre is located and confirmed live. Addresses always come from the publisher’s own pages, never from a search engine — several of these help centres are impersonated by pages carrying fake support telephone numbers.
  2. A gathering script is written for that estate and run locally. It reads plainly where plain requests work and raises a real browser only where they do not, waits for a page’s content rather than its file size, resumes after interruption, and writes a log that says in plain words what happened.
  3. The saved pages are assembled into one document, using the help centre’s own categories where it publishes them.
  4. The result is checked against the quality gates below and released only when every one of them is clean.

Quality gates

No guide ships unless all of these pass:

  • Every heading appears in the table of contents, and every contents entry points at a real heading.
  • No broken internal links.
  • No bare web addresses, and no link whose visible text is an address — both read badly aloud.
  • No navigation remnants: no “skip to content”, no cookie notices, no “was this article helpful”, no stray markup.
  • Headings nest properly, so a heading list is navigable.
  • The file parses cleanly through Pandoc, carries a byte-order mark, and uses Windows line endings.

Scope conventions

Guides cover the surfaces a person actually uses: the Windows program, the web version, the iPhone or iPad app, and the Alexa skill, wherever each exists. Each guide’s preamble says which of those the product has — many have only one or two.

Consistently excluded, and always named where excluded:

  • Developer APIs and integration documentation.
  • Administrator material: the settings for running an organisation’s estate rather than using the product.
  • Estates written for a different audience — drivers, couriers, merchants, publishers, member stations — which would deserve their own volumes.
  • Contact forms, ticket queues, chat assistants and virtual agents, which hold nothing to read.

Honesty about limits

  • Each guide is a snapshot, taken on the date in its preamble. Help centres change; a guide does not update itself.
  • Where a publisher offers no categories, the grouping is editorial, and the preamble says so rather than passing my arrangement off as theirs.
  • Some estates could not be gathered, and are recorded rather than papered over with third-party writing. The reasons vary: a publisher’s help may sit behind a check that refuses automated reading; it may exist only inside the app or the extension, with nothing published on the web at all; or a company may simply publish no written guidance, answering through a chat assistant or a telephone line instead. Several products in this collection are thin for exactly that reason, and their preambles say which reason applies.
  • Some guides are thin because the help is thin. A product that answers through a chat assistant has little written guidance, and the guide says so instead of padding.
  • Some are large in unexpected places. One delivery service files the terms of every promotion as a help article; those are kept, and the preamble points to where the how-to material actually lives.

Reading a guide with a screen reader

The guides are plain Markdown and can be read in any editor. A few things make them quicker:

  • The heading structure is only three deep by design, so a heading list is a usable index rather than a wall.
  • The table of contents at the top links to every article, so jumping is a matter of following a link rather than scrolling.
  • Because everything is one file, a find command searches the entire product’s help at once — often faster than any help centre’s own search box.
  • An HTML rendering of this file sits beside it as README.htm, and any guide can be rendered the same way with Pandoc: pandoc -s -o Netflix.htm Netflix_Help_Guide.md
  • HowTheseGuidesWereMade.md, also in this repository, explains how to build a guide for an app that is not here yet, and includes a prompt you can copy.
