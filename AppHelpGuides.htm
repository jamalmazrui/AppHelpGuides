How These Guides Were Made

If you have read one of these guides and thought “I wish this existed for the app I use every day” — you can make it. This page explains how the collection was built, what you need, what goes wrong and how to get past it, and it ends with a prompt you can copy and paste into Claude to start your own.

Nothing here requires you to be a programmer. You need to be able to run a command, upload a file, and describe what you want.

The idea in one paragraph

A help centre is a few hundred short answers scattered across a few hundred web pages, each wrapped in navigation, banners, chat widgets and scripts. All of that is furniture for a sighted mouse user and obstruction for the rest of us. The trick is simply this: fetch the pages once, keep the words, throw the furniture away, and put everything into a single well-structured file that you can read straight through, jump around by heading, or search in one go. The words stay the publisher’s own. Only the shape changes.

What you need

  • A Windows PC with your screen reader, and Microsoft Edge installed. Edge is already there on Windows.
  • Python, from python.org. During installation, tick the box that adds Python to your PATH.
  • Playwright, which lets a script drive Edge. In a command prompt: pip install playwright. Some help centres need this; many do not.
  • Claude, at claude.ai, on a plan that lets you upload and download files.
  • A folder to work in, such as C:\AppHelpGuides.

That is the whole toolkit. There is nothing to configure.

The cycle

Each guide follows the same five steps. The first one takes an evening; after that they take under an hour, and most of that is waiting.

  1. Ask. Tell Claude which app you want, and on which surfaces you use it — the Windows program, the website, the phone app, an Alexa skill. Claude finds the publisher’s real help centre and confirms it is live before writing anything.
  2. Receive a script. Claude writes a gathering script for that particular help centre and sends it to you. It is a single Python file. You do not need to read it.
  3. Run it. Put it in your folder and run it: python getNetflixHelp.py. It writes two things: a zip archive of the pages it saved, and a log that says in plain words what happened.
  4. Send both back. Upload the zip and the log to Claude. The log matters as much as the zip — it is how problems get diagnosed.
  5. Get your guide. Claude assembles the pages into one document, checks it against a list of quality rules, and sends it to you.

If step three goes wrong, that is normal and it is not your fault. Send the log anyway. Half the guides in this collection took two or three attempts, and every attempt taught the next one something.

What makes a good guide

Ask for these, because they are what turn a pile of pages into something pleasant to read:

  • One file. Not a folder of files, not a website. One document per product.
  • Three heading levels, no more. The guide title, a section, an article. A heading list should be an index, not a wall.
  • A table of contents that matches — every article listed, every entry a working link.
  • A preamble that tells the truth: where the text came from, on what date, which surfaces the product actually runs on, and what was deliberately left out.
  • No furniture. No “skip to content”, no cookie notices, no “was this article helpful”, no stray markup.
  • Cross references as internal links, so a “see also” never leaves the file.
  • Tables turned into lists, which read far better aloud.
  • Scope stated, not silently assumed. If a publisher’s help covers drivers, merchants and customers, say which one the guide holds.

Ask Claude to check every one of these before sending you the file, and to tell you if any fails.

Things that go wrong, and what they mean

These are the failures this collection actually hit. Knowing them saves hours.

  • The log stops right after “Using installed Microsoft Edge”. Another browser-driving script is still running. Only one at a time. Let the first finish, then run the second.
  • Pages save, but the guide comes out nearly empty. The script saved the page’s shell before the help was filled in. Modern help centres send a large empty frame instantly and pour the words in a moment later. Tell Claude the pages have no text in them; the cure is to wait for content rather than for page size.
  • The zip is too big to upload. Ask Claude for a shrinking script. It keeps the article from each page and throws the rest away, then splits the result into parts small enough to send.
  • The upload truncates silently. If Claude says the archive is cut short, it usually is. Shrink it and send it in parts.
  • The run goes on forever, opening pages in other languages. The address rules were too loose. Stop it, and tell Claude what you saw — it is a one-line fix.
  • Everything comes back blank after the first page or two. The site is rate-limiting the browser. Ask for pacing between pages.
  • Searching for a help centre returns rubbish. Several are impersonated by pages carrying fake support telephone numbers. Never take an address from a search result. Ask Claude to read the publisher’s own footer instead — that is how the Expedia and BBC help centres were finally found.
  • Nothing works, three ways running. Some help exists only inside an app, or behind a check that refuses automated reading. Record it and move on. Two or three products in this collection ended that way, and saying so is more useful than pretending otherwise.

Habits worth copying

  • Run one browser job at a time. Most of the wasted hours came from ignoring this.
  • Keep the logs. Every real diagnosis in this project came from a log, not from a guess.
  • Let the publisher’s own categories set the structure where they exist. Ask Claude to say so plainly when the grouping is its own invention instead.
  • Do not accept a summary. The whole point is the publisher’s own words. If a guide is thin, it should be thin because the help is thin, and the preamble should say which.
  • Ask what was left out. A good guide names its exclusions.
  • Convert to HTML for daily reading. The guides are written as Markdown and render to a single HTML file with one command: pandoc -s -o Netflix.htm Netflix_Help_Guide.md

The prompt

Copy everything between the lines into Claude, replacing the app name and the surfaces with your own. You can paste it as your very first message.

I am a screen reader user. I want to build a single-file, screen-reader-friendly
guide containing the complete official help documentation for one app, so I can
read and search it all in one place instead of clicking through a help centre.

The app is: [NAME OF APP]
I use it on: [e.g. Windows, the website, my iPhone]

Please work with me like this:

1. First, find the publisher's own help centre and confirm it is live. Take the
   address from the publisher's own pages, never from a search result -- some
   help centres are impersonated by pages with fake support phone numbers. Tell
   me what you found and what its structure looks like before writing anything.

2. Then write me a single self-contained Python script that gathers it. I will
   run it on Windows and send you back what it produces. Please make it:
   - use plain requests where they work, and a visible Microsoft Edge only where
     they do not
   - wait for a page's actual content to appear, never just for the page to be
     big, because many help centres send a large empty frame first
   - stop with a clear message if the browser does not open within two minutes,
     since that means another script is already using it
   - stay inside the audience I want, and exclude other audiences such as
     drivers, merchants or administrators
   - resume over pages it already saved if I run it twice
   - save a zip archive and a log that says in plain words what happened,
     including a final verdict line

3. I will upload the zip and the log. Please diagnose anything that went wrong
   from the log rather than guessing, and tell me plainly if a run failed.

4. Then build the guide as one Markdown file with:
   - a preamble saying where the text came from, on what date, which surfaces
     the product runs on, and what was deliberately left out
   - a table of contents listing every article as a link
   - exactly three heading levels: guide title, section, article
   - the publisher's own categories as sections where they publish them, and a
     clear statement in the preamble when the grouping is your own
   - cross references between articles turned into internal links
   - tables rewritten as lists, which read better aloud
   - no navigation remnants, no cookie notices, no "was this article helpful"
   - the publisher's own words throughout, not summaries

5. Before sending it, check that every heading appears in the contents, that no
   internal link is broken, that there are no bare web addresses and no link
   whose visible text is an address, and tell me the result of those checks.

Deliver the guide as a .md file inside a zip archive, with the file at the root
of the archive.

If the first script fails, paste the log back and say what you saw on screen. That is genuinely all the diagnosis Claude needs.

After the first guide

Once you have one, the rest are quicker. A few things worth doing:

  • Keep them together in one folder, and consider a GitHub repository so others can download the lot.
  • Render them to HTML so they open in a browser and read comfortably from top to bottom.
  • Re-gather occasionally. Help centres change; a guide is a snapshot with a date on it.
  • Share the ones you make. The collection this page describes grew from one guide to more than forty. Yours may cover an app nobody has done yet.

The help text in any guide belongs to the company that wrote it. These documents are format conversions made for accessibility — the same words, in a shape a screen reader can move through efficiently — and they are no substitute for the publisher’s own help centre when you need the very latest answer.
